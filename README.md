# Лабораторная работа 3. Сервис тикетов техподдержки

За одну пару (90 минут) соберите в группе из 4–5 человек внутренний сервис HelpDesk Lite на FastAPI. Пользователь заводит тикет, меняет его приоритет и отслеживает статус до закрытия. Тикеты хранятся в памяти одного процесса. После перезапуска сервера список снова пуст.

К концу работы у группы должны быть запускаемое приложение и краткое описание контракта тикета. На защите покажите сценарий работы API, объясните переходы статуса и одно архитектурное решение группы.

## Первый запуск

Нужен Python 3.10 или новее. Выполните команды из корня репозитория. В Windows для активации окружения в PowerShell используйте `.\.venv\Scripts\Activate.ps1` вместо команды `source`.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m uvicorn starter:app --reload
```

Откройте [Swagger UI](http://127.0.0.1:8000/docs). В стартовой версии уже видны все пять операций. Вызовы с корректными данными будут возвращать ошибку 500, пока вы не реализуете методы с `raise NotImplementedError`.

## Что реализовать

Работайте в [starter.py](starter.py). В нём уже есть Pydantic-модели, настройки, зависимости FastAPI и обработчики ошибок. Найдите все заглушки `raise NotImplementedError`, в том числе без комментария `TODO`.

| Запрос | Ожидаемое поведение |
| --- | --- |
| `POST /tickets` | Создать тикет и вернуть его с кодом 201. Обязателен непустой `title`. Поля `description` и `assignee` необязательны. Приоритет по умолчанию — `normal`. Сервер назначает уникальный `id`, время `created_at` и начальный статус `open`. |
| `GET /tickets` | Вернуть страницу с кодом 200. В ответе `items` содержит тикеты запрошенной страницы, `total` — число всех тикетов, `page` — номер страницы, `page_size` — применённый размер. |
| `GET /tickets/{ticket_id}` | Вернуть тикет с кодом 200. Если такого идентификатора нет, вернуть 404. |
| `PATCH /tickets/{ticket_id}` | Изменить только переданные поля из `description`, `priority`, `assignee`, `status` и вернуть обновлённый тикет с кодом 200. При запрещённой смене статуса вернуть 409 и сохранить прежние данные. Для отсутствующего тикета вернуть 404. |
| `DELETE /tickets/{ticket_id}` | Удалить тикет и вернуть 204 с пустым телом. Если тикет отсутствует, вернуть 404. |

**Сортировка и страницы.** Для `sort_by` допустимы `created_at` и `priority`, для `order` — `asc` и `desc`. По умолчанию первыми идут самые новые тикеты. Порядок приоритетов по возрастанию — `low`, `normal`, `high`, `urgent`. Отсортируйте весь список перед выборкой страницы. Нумерация страниц начинается с 1. Если `page_size` пропущен, используйте `settings.default_page_size` (5), если превышает максимум — ограничьте его до `settings.max_page_size` (20). Для страницы за пределами списка верните пустой `items`. Недопустимые значения `sort_by`, `order`, а также `page` или `page_size` меньше 1 должны давать 422 при валидации запроса.

**Статусы.** Допустимые смены статуса заданы в `ALLOWED_TRANSITIONS`. Из `open` тикет можно взять в работу (`in_progress`). Из `in_progress` его можно вернуть в `open` или перевести в `resolved`. Из `resolved` его можно снова взять в работу или закрыть (`closed`). У закрытого тикета больше нет переходов.

**Слои приложения.** В `TicketRepository` реализуйте операции с хранилищем. В `TicketService` разместите правила создания и изменения тикета, сортировку и пагинацию. В эндпоинтах вызывайте сервис через существующие зависимости. Для отсутствующего тикета и недопустимой смены статуса используйте исключения, объявленные в заготовке. Их обработчики формируют HTTP-ответ с полем `detail`. Сохраните в Swagger UI теги, краткие описания, модели ответов и коды статусов операций.

## Как проверить результат

В Swagger UI выполните запросы подряд за один запуск сервера.

1. Через `POST /tickets` создайте тикет с телом `{"title":"Не открывается отчёт","priority":"high"}`. Создайте ещё два с приоритетами `urgent` и `low`. Сохраните идентификатор первого тикета.
2. Вызовите `GET /tickets` без параметров и проверьте порядок по времени создания. Затем задайте `sort_by=priority`, `order=desc`, `page=2`, `page_size=1`. На второй странице должен оказаться тикет с приоритетом `high`, а `total` должно равняться 3.
3. Запросите список с `page_size=21` и проверьте, что в ответе `page_size` равно 20. Затем отправьте `sort_by=title` и проверьте код 422.
4. Получите первый тикет по ID. Отправьте для него PATCH с телом `{"assignee":"alex","status":"in_progress"}`. Проверьте, что исполнитель и статус изменились, а заголовок и приоритет сохранились.
5. Отправьте PATCH с телом `{"status":"closed"}` для того же тикета. Проверьте код 409 и поле `detail`. Повторным GET убедитесь, что статус по-прежнему `in_progress`.
6. Удалите тикет. Проверьте код 204 и пустое тело ответа. Повторный GET по этому ID должен вернуть 404 с описанием ошибки.

## Описание контракта

Кратко опишите контракт своего приложения в свободной форме, например в начале `starter.py`. Укажите поля клиента и сервера при создании, допустимые приоритеты и статусы, изменяемые через PATCH поля и разрешённые переходы. Для списка укажите сортировку по умолчанию, стандартный и максимальный размер страницы. Для ошибок укажите коды при отсутствии тикета и запрещённом переходе.
